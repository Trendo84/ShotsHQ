# v1.1: export-only bezel overlay

## Why

User feedback during the v1 editor bug pass: people see the canvas at
1290×2796 and expect an iPhone bezel rendered around it. The current
architecture is "canvas IS the screen, no bezel" — documented in
`CLAUDE.md → Editor canvas model` so future contributors don't try to
wrap the editing canvas in a Fabric Group.

But there ARE legitimate use cases for a bezel-wrapped composition:

- Marketing / press-kit images ("here's our app on a real phone")
- Social cards (OG, Twitter, LinkedIn) that read better with chrome
- Web hero shots where the screen alone looks naked

These are **export-time** concerns, not edit-time. The user's editing
experience stays the canvas-is-screen model (no bezel, max screen real
estate, exact App Store dimensions). On export, an additional render
path can compose the bezel around the screen output.

## What

Add a new export surface: `bezel-shot`. Output dimensions match a real
device photograph (e.g. 1500×3000 for a centred iPhone 16 Pro Max with
margin), with the existing 1290×2796 screen render composited inside a
high-quality bezel SVG/PNG.

Architecture:

- `lib/render/bezel.ts` — pure function that takes a screen render
  (1290×2796 PNG buffer) and a device + bezel-asset choice, returns a
  composited PNG buffer.
- `public/bezels/iphone-16-pro-max.svg` (and friends) — vector bezel
  assets, sourced from Apple's marketing-assets pages or hand-traced.
  No real Apple photography.
- New Trigger.dev task `render-bezel-shot` that wraps the existing
  `render-screenshot` output and composites bezel on top.
- New surface entry in `lib/surfaces/catalog.ts` (`bezel-shot`,
  pro-tier).
- Optional in-editor "preview with bezel" toggle that's READ-ONLY —
  shows the user what the export will look like without changing the
  editing canvas. Tucked under a small toggle so the default editing
  view stays naked.

## Why NOT in the editing canvas

If the bezel rendered inside Fabric:
- Layer coords would have to compensate for bezel inset → either every
  layer's x/y becomes "relative to screen origin inside the bezel" (a
  schema migration that breaks existing projects), or the bezel
  becomes a non-Fabric overlay that eats clicks.
- The canvas would no longer be 1290×2796 — it'd be the bezel's outer
  dim (~1500×3000), which means user-authored work would be at the
  wrong absolute coordinates for a real App Store render.
- Server render via `sharp` would have to know to subtract the bezel
  from the export. Two render targets diverging from one editor state.

Export-only overlay sidesteps all of this: the editor authors the
screen at exact App Store dims, the export pass adds bezel chrome at
the rendering boundary.

## Tests

- Vitest: `lib/render/bezel.ts` composes a known input → known output
  (snapshot the buffer hash).
- Trigger.dev: dispatch `render-bezel-shot`, assert R2 URL is
  reachable, assert dimensions match expected output.

## Out of scope

- Real device photography (e.g. iPhone 16 Pro Max in someone's hand).
  Stick to vector bezels — they're brand-neutral, infinitely scalable,
  and don't require licensing.
- Animated bezel previews (e.g. tilt, perspective). The static front
  render is enough for v1.1.
- Bezel customization (colour, finish). Use Apple's standard finishes
  for the modeled device.
