# v1.1: multi-frame canvas schema

## Why

Today `ShotsCanvas` is single-frame: one project = one canvas with one
background + one layers array. The right rail in the editor displays a
single `[ FRAME · 01 ]` card with a disabled "+ ADD · SOON" button — UI
honest about the limitation but functionally a dead end.

Apple's App Store screenshot carousel takes **5–10 screenshots per device**.
A real ShotsHQ project should let the user assemble that carousel inside
one project, not force them to spin up 5–10 sibling projects.

## What

Extend `ShotsCanvas` with a `frames: ShotsFrame[]` field where each
`ShotsFrame` owns:

- `id` (uuid or short slug, "01" / "02" / etc.)
- `background: ShotsBackground`
- `layers: ShotsLayer[]`
- optional `locale?: string` (so the same frame can fork by locale once
  translate fan-out lands per-frame)

The `device` + `width` + `height` fields stay at the canvas level —
every frame in a project shares dimensions.

```ts
export type ShotsFrame = {
  id:         string;
  background: ShotsBackground;
  layers:     ShotsLayer[];
  locale?:    string;
};

export type ShotsCanvas = {
  version:    "1";    // bump to "2" for the migration
  device:     DeviceId;
  width:      number;
  height:     number;
  frames:     ShotsFrame[];
};
```

## Migration

`projects.polotnoJson` shape changes. One-shot script at
`scripts/migrate-canvas-v2.ts` wraps existing single-canvas data into
`{ version: "2", device, width, height, frames: [{ id: "01", background, layers }] }`.

Idempotent — checks `version` field, skips if already migrated.

## Touch points

- `lib/canvas/schema.ts` — schema additions, `ShotsFrame` type
- `lib/canvas/defaults.ts` — `defaultCanvas()` returns a 1-frame array
- `components/editor/FabricCanvas.tsx` — accepts an active `frameId` prop;
  re-mounts when it changes (already keyed on projectId; extend to
  `[projectId, frameId]`)
- `components/editor/EditorClient.tsx` — `useState<frameId>` plus
  per-frame layer broadcast
- `components/editor/RightPanel.tsx` — drive `FRAMES` from real
  `project.polotnoJson.frames`. Visual structure is already preserved
  for this — work is purely additive (replace the const-of-1 with the
  real array; clicks set `frameId` in EditorClient).
- `app/actions/canvas.ts` `saveCanvas` — accepts `frameId` and patches
  only that frame, not the whole canvas
- `lib/db/queries/projects.ts` `updateProjectCanvas` — same patching
  semantics

## Tests

- Vitest: round-trip a v1 canvas through the migration script, assert
  frames[0] matches the original.
- Vitest: 2-frame canvas, mutate frame 02's layers, save, reload, assert
  frame 01 unchanged.
- Playwright (once auth bypass lands — see issue v1.1: Playwright auth
  bypass): switch frames in the right rail, verify each loads its own
  layers; add a frame; delete a frame.

## Out of scope

- Per-frame device dimensions (every frame shares the canvas
  device + dims; cross-device exports are a separate v1.2 concern).
- Inter-frame layer linking ("change this once, propagate to all
  frames") — useful but a separate UX problem.
- Multi-locale auto-fork — translate fan-out should populate per-locale
  copies of each frame, but that wires up after the schema lands.
