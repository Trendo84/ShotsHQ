# v1.1: template tier gating

> **Status:** Captured 2026-05-01 · Not yet opened on GitHub · See [README.md](./README.md)
>
> **Related:** Surfaced during triage of [docs/audits/2026-04-30-comet-sonnet-editor.md](../audits/2026-04-30-comet-sonnet-editor.md) finding #1. The auth-aware template-card routing fix in that triage's commit 2 unblocks the basic logged-in / anonymous case but leaves the tier-gating question open.

## Why

The `/templates` page exposes 21 templates split between Free (`tag: "Free"`) and Pro (`tag: "Pro"`) tiers. Clicking any card today routes the user to `/projects/new?template=<slug>` (commit 2 of the audit triage on 2026-05-01) regardless of the user's plan. That's correct for Free templates and any plan tier. It's WRONG for a Pro template clicked by a Free-tier user — they'll land in the wizard, seed the form, commit, then discover at export time that the template's premium features (Pro-only surfaces, watermark removal, etc.) aren't unlocked.

The bug is "we let them start" not "they shouldn't have access." Two correct routes:

- Free user clicks a Pro template → preview the template, but the CTA reads "Pro plan required · upgrade to use" with a Stripe checkout deep-link. Don't seed the wizard.
- Studio / Lifetime user clicks any template → straight to `/projects/new?template=<slug>` (current behavior).

This issue is small but matters for the conversion funnel: it's the first moment a free user sees the value of upgrading, framed by a specific template they want.

## What

Three pieces, each small:

### 1. Add `tier: "free" | "pro"` to the canonical Template type

Already de-facto present as `tag: "Free" | "Pro"` in the catalog (`lib/templates/catalog.ts` after commit 2 of the audit triage). Rename to `tier` for code clarity and lowercase the values.

```ts
type Template = {
  slug:    string;
  name:    string;
  tier:    "free" | "pro";
  // …existing fields…
};
```

### 2. Tier-aware routing in `TemplateCard`

In `components/marketing/Templates.tsx`'s `TemplateCard`, the `useUser()` flow added in commit 2 already differentiates signed-in vs anonymous. Extend with plan check:

```ts
const { isLoaded, isSignedIn, user } = useUser();
const userPlan = (user?.publicMetadata?.plan as string) ?? "free";
const isUnmetered = ["studio_monthly", "studio_annual", "lifetime"].includes(userPlan);

const href = !isLoaded
  ? `/sign-up?redirect_url=${encodeURIComponent(...)}`
  : !isSignedIn
  ? `/sign-up?redirect_url=${encodeURIComponent(...)}`
  : t.tier === "pro" && !isUnmetered
  ? `/billing?upgrade_for=template&slug=${t.slug}`
  : `/projects/new?template=${t.slug}`;
```

Plan field comes from Clerk's `publicMetadata.plan` (already populated by the Clerk webhook on Stripe subscription events — see `app/api/webhooks/clerk/route.ts` if not, this is a one-line addition).

### 3. `/billing` upgrade-for-template handler

When `?upgrade_for=template&slug=<slug>` is present on `/billing`, surface a small inline panel above the credit packs: "You clicked the **Mono Punch** template. It's a Pro template — choose a Studio plan below to unlock it." The CTA on the chosen Studio pack auto-includes `?next=/projects/new?template=<slug>` so post-checkout returns the user to the seeded wizard.

This is a 30-line addition to `app/(app)/billing/page.tsx` and the `PurchaseButton` component.

## Touch points

- `lib/templates/catalog.ts` — `tag` → `tier`, lowercase values
- `components/marketing/Templates.tsx` — extend the `useUser()` href branching with plan check
- `app/(app)/billing/page.tsx` — read `?upgrade_for=template&slug=<slug>` query param, render upgrade panel
- `components/billing/PurchaseButton.tsx` — accept an optional `successNext` prop, append to the Stripe checkout success URL
- `app/api/stripe/checkout/route.ts` — honor `?next=` in the body, validate same-origin (apply the same redirect-validation pattern as `app/(auth)/sign-up/[[...sign-up]]/page.tsx` after commit 2 of the audit triage)
- `app/api/webhooks/clerk/route.ts` — verify `publicMetadata.plan` is populated on subscription events; if not, add the metadata write

## Tests

- `tests/templates/tier-gating.test.ts` — pure-logic test of the URL builder. Given `(slug, isSignedIn, plan, tier)`, returns the expected URL. Covers the four real cases (anon any tier, free user free template, free user pro template, paid user any tier) plus the `!isLoaded` SSR case.
- Playwright spec: anon → click pro template → land on /sign-up; signed-in free user → click pro template → land on /billing with the upgrade panel; signed-in studio user → click pro template → land on /projects/new with template seeded.

## Out of scope

- Trial mechanics (free users get N pro template uses before paywall). Probably worth doing but a separate feature, not bundled here.
- Per-template featured-tier overrides. Some Pro templates might be "free this week" promotions — a future content-flag, not part of this issue.
- Direct-from-marketing template upgrades (anonymous clicks Pro template → plan picker before sign-up). Adds funnel complexity for unclear ROI; punt.
